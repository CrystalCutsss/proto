# 0001. Рабочая модель: облачные сессии, фаза = ветка = PR, STATUS.md

- Статус: Принято
- Дата: 2026-10-13
- Фаза: 0

## Контекст
- Владелец среды работает только из браузера: claude.ai/code, GitHub, Google Cloud, панель хостинга.
- Каждая облачная сессия — свежий клон репозитория во временной VM. Всё, что не запушено, может пропасть при перезапуске VM. В Фазе 0 рабочий процесс перезапускался несколько раз.
- В сессию переносятся только закоммиченные `CLAUDE.md`, `.claude/` и `.mcp.json`. Плагины из настроек репозитория не устанавливаются ([cloud-environments](https://code.claude.com/docs/en/cloud-environments#what-carries-over-from-your-setup)).
- GitHub-прокси сессии не поддерживает GraphQL, поэтому `gh pr`/`gh issue` не работают. Он не ограничивает, в какие ветки идёт push (см. [аудит](../setup/environment-audit.md#3-github-через-прокси-сессии)).

## Варианты
1. **Одна длинная сессия на всю работу.** Контекст копится и сжимается, а при потере VM теряется незапушенное.
2. **Фазы с ветками и PR, состояние в репозитории.** Каждая фаза — отдельная ветка от свежего `main` и один PR. Состояние и следующий шаг лежат в `docs/STATUS.md`. Новая сессия продолжает по команде «Прочитай docs/STATUS.md и продолжи».
3. **Projects в claude.ai** (параллельные облачные сессии под управлением одной). Полезно для пакетной работы, но избыточно для последовательных фаз с ручным мержем. Оценим в Фазе 4 (ADR об оркестрации).

## Решение
Вариант 2:
- **Одна фаза или задача — одна ветка — один PR в `main`.** Ветка создаётся от свежего `origin/main` после мержа предыдущей фазы. Имя — `phase/<N>-<slug>` или ветка `claude/*`, которую выдала сессия.
- **В конце фазы:**
  - отчёт: что сделано, как проверено, открытые вопросы, что сделать в браузере;
  - PR;
  - остановка до «go» владельца.
- **`docs/STATUS.md` обновляется в каждом PR:** текущая фаза, готово, заблокировано, следующий шаг, ожидаемые действия владельца.
- **Частые push.** Минимум — после каждого логически завершённого шага.
- **PR создаются** GitHub-инструментами сессии (`create_pull_request`) или `gh api -X POST repos/CrystalCutsss/proto/pulls`.
- **Существенные решения оформляются как ADR.**

## Последствия
- Работу можно продолжить из любой новой сессии без потери контекста.
- Владелец контролирует каждый шаг мержем. Это даёт задержку между фазами, но исключает незаметный дрейф.
- `gh pr …` запрещено использовать в skills и инструкциях. Вместо него — REST или MCP.
- Пересмотреть, если появятся параллельные потоки работ (пакетное создание прототипов): тогда нужен ADR об оркестрации (Фаза 4).
